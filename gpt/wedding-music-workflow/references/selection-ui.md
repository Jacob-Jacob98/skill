# 版本选择交互

用户希望点击候选完成选择，不需要抄写编号或输入“1A、5B”。这一步由聊天界面的交互工具呈现，Python 下载脚本不会生成聊天按钮。

## 使用当前环境的选择工具

在提供 `functions.request_user_input_async` 的 Codex 会话中优先调用该工具：

- 每首不确定的歌曲对应一个 `questions` 元素；通常每批 2–3 首，歌曲较多时分批呈现。每个题目独立，保留原歌单序号。
- `title` 只包含该首的序号、环节（若有）、歌名、需要确认的版本和试听状态；不要把全部候选写成长段题干。
- **必须提供 `options` 字符串数组。** 每个元素就是一个可点击候选，例如“演奏者｜专辑或版本｜3:28”。标题和选项同时提供足够信息，能区分录音。
- 每首优先展示 2–4 个匹配度较高的真实候选；不要为了凑选项编造版本。若只有一个待确认候选，可提供“使用这条……”和“继续搜索”两个明确行动。
- UI 已提供自由填写入口，不再加入“其他”或“自行输入”等占位选项；不要在题目中要求回复字母编号。
- 工具异步返回后可以继续处理已确认歌曲；收到选择消息前，歧义条目保持未确认。

工具参数结构示例（示例演奏者不是真实搜索结果，执行时必须替换）：

```json
{
  "questions": [
    {
      "title": "第1首「主持人开场」《示例钢琴曲》选哪一版？QQ音乐候选，均未试听。",
      "options": [
        "演奏者甲｜钢琴独奏专辑｜3:28",
        "演奏者乙｜现场钢琴版｜4:05"
      ]
    },
    {
      "title": "第5首《示例歌曲》选原版还是重录版？均未试听。",
      "options": [
        "原唱歌手｜原专辑版｜3:56",
        "原唱歌手｜重录专辑版｜3:55"
      ]
    }
  ]
}
```

其他环境可能使用不同名称或参数，只调用实际可用的工具并遵守其 schema。`request_user_input` 若仅限 Plan 模式，就不能在普通执行模式调用。不能以“集中确认”为由退回无选项的长文本输入框。

## 把选择对应到下载任务

发问前记录“原歌单序号 → 当前 session → 选项文字 → candidate_id”。歌单序号与候选 ID 是不同字段，不能直接把第几首当作候选编号。选项文字需能唯一对应一个候选；同名同长时加入版本、专辑或平台信息。

仅在用户实际提交选择后，将该选项对应的真实 `session`、`candidate_id` 写入独立确认清单，并设 `confirmed:true`。首次预选、跳过、关闭、无回复和超时都不能视为用户确认。部分回答只确认对应曲目，其余保持待选；自由填写的版本要核对或继续搜索，不能映射到最相似选项后直接下载。

同一任务已经确认的版本继续沿用，除非候选失效、结果变化或用户要求重选。不要为了演示交互让用户重复选歌。没有选择工具时说明限制，使用简短文字备选；不能承诺该环境出现按钮，也不能假装已经展示或收到选择。
